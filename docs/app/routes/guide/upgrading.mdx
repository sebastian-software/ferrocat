# Releases And Upgrading

Ferrocat follows semantic versioning from `1.0` onward: breaking API changes
ship in a new major version, while minor and patch releases stay backward
compatible. The `2.1.0` release was a reviewed, one-time exception for removing
accidental public coupling while the user base was still small. That cleanup
window is closed. Start every upgrade from the changelog and keep the workspace
crate versions aligned.

## Upgrading from 3.x to 4.0

Upgrade the Ferrocat crates and host integrations together. The four published
crates use the same version. Validate catalogs before deploying regenerated
runtime artifacts.

### Runtime quotes and derived IDs

`RuntimeLiteralApostrophes` now starts a literal quote before `<`, as it already
does before braces. For example, `Use '<name>' here` means literal text rather
than a rich-text tag. Unquoted `<link>{name}</link>` remains a real tag. Review
messages containing an apostrophe before `<` for their intended meaning.
`Strict` remains the default syntax policy and its raw key helper is unchanged.

Regenerate source-extracted runtime IDs, `CompiledCatalogIdIndex` values,
compiled artifacts, generated bundles and dependent caches together under the
same syntax policy. Do not mix a 3.x extractor's cached IDs with a 4.0 compiler.
The hash algorithm and raw PO identities have not changed; affected policy
canonicalization has. There is no additional legacy runtime policy.

### FCL2 storage

Writers emit `%FCL2`; readers accept FCL1 and FCL2 by their header. In FCL2 the
context column is `n` for no context, `s` for an explicitly empty context, or
`s` followed by escaped context text. Carriage returns are escaped as `\r`.

Upgrade every FCL reader before rewriting catalogs. To migrate an existing
file, call `convert_catalog_file` with FCL input and FCL output (the same path
is supported after validation). The existing `CatalogMode::IcuFcl` selects the
current writer; no new storage-mode enum variant is needed. An ordinary update
also rewrites FCL1 as canonical FCL2, even if message content is unchanged.

FCL1 already conflated absent and empty contexts and could lose a terminal
carriage return. Migration preserves the information still observable in FCL1.
Recover lost information from an authoritative original PO catalog when needed.
See the [format decision](/architecture/adr/0033-lossless-fcl2-context-and-carriage-returns).

### Artifact compilation defaults

`CompileCatalogArtifactOptions::new` now sets `strict_icu` to `true`. Full,
selected and provenance-report compilation return an error for invalid final
ICU syntax. Diagnostic tools that need to collect all errors opt in explicitly:

```rust
let options = CompileCatalogArtifactOptions::new("de", "en")
    .with_strict_icu(false);
```

Inspect the resulting diagnostics before publishing such an artifact. This
setting controls syntax failures; source/translation compatibility and runtime
formatter-support diagnostics retain their separate policies.

Report options now have one ICU configuration. Replace assignments to
`report.icu_options` with `report.options.icu_options`, or use
`report.with_icu_options(...)`. The full, selected and report paths all use
that nested value. The artifact JSON schema remains version 1.

### Diagnostic code types

`ferrocat_po::DiagnosticCode` and `ferrocat_icu::DiagnosticCode` are distinct in
every feature profile. Enabling `catalog` no longer changes their type identity.
At a cross-crate boundary use `.into()` with `catalog` enabled, or transport the
canonical string when using the lean PO profile. JSON diagnostic codes remain
plain strings with unchanged spelling.

### Correctness changes

The ICU parser rejects duplicate selectors (including equivalent numeric
selectors) and repeated plural offsets. Fix ambiguous patterns before upgrading.
The serializer preserves quoted syntax and formatter-style literals, so their
canonical output spelling can change. Existing Unix file permissions survive
atomic catalog replacement. The CLI rejects a target `--locale` filter equal
to `--source-locale` instead of reporting success for zero target locales.

## Where release notes live

- [GitHub Releases](https://github.com/sebastian-software/ferrocat/releases)
  gives the repository-level release view.
- [`ferrocat` CHANGELOG](https://github.com/sebastian-software/ferrocat/blob/main/crates/ferrocat/CHANGELOG.md)
  is the best starting point for application users of the umbrella crate.
- Direct sub-crate users should also read the matching `ferrocat-po` or
  `ferrocat-icu` changelog for low-level parser, catalog, or ICU changes.

Release Please generates these changelogs from Conventional Commits. Breaking
changes normally use a major-release marker such as `feat!:` or a
`BREAKING CHANGE` note so they are visible in release notes and changelog
sections. The historical `2.1.0` cleanup exceptions are documented in that
release's notes without a major-release marker.

MSRV bumps follow the same release-note rule. Ferrocat aligns its declared MSRV
with OXC when practical while avoiding churn from tracking only the newest
stable toolchain. Raising the MSRV is treated as a minor-version change and
called out in the changelog; patch releases should not raise the MSRV.

## Lockstep versions

The public library crates are released in lockstep: every release advances all
of them to the same version. In normal application code, prefer depending on the
umbrella crate:

```toml
[dependencies]
ferrocat = "4"
```

If you depend on lower-level crates directly, keep every Ferrocat crate on the
same version line so you get the combination that was released and tested
together:

```toml
[dependencies]
ferrocat-po = "4"
ferrocat-icu = "4"
```

Within a normal major line, minor and patch releases stay backward compatible, so
Cargo resolves a shared `"4"` requirement to a single, latest-compatible
version. Avoid pinning the umbrella crate and a direct sub-crate to different
exact versions, for example `ferrocat = "=4.0.0"` with `ferrocat-po = "=3.0.0"`:
that can pull two copies of the Ferrocat types into the build and fail with
confusing type-mismatch errors.

The 2.2 release history includes a temporary `3.0.0` publication from when the
self-closing-tag change was first classified as breaking. Those packages were
yanked and the compatible change shipped as `2.2.0`. Use the 2.2 line rather
than selecting `3.0.0` from the historical changelog entries.

## Earlier 3.x migration notes

Ferrocat 3.2.0 canonicalized runtime-apostrophe artifact messages and compiled
IDs. Regenerate runtime artifacts and `CompiledCatalogIdIndex` values created
with 3.1.0 or earlier. It also restored fuzzy review: coverage, fuzzy-enabled
audit, and current review targets require `parse_catalog_for_review` or an
explicit `into_normalized_view_assuming_no_fuzzy` for programmatic catalogs.
Active PO and FCL fuzzy entries no longer count as translated, and CLI audit
reports them. The fuzzy status, coverage accessor, audit check, and diagnostic
are available again. Explicit PO/FCL conversion preserves shared metadata.

In 3.2.1, FCL update, conversion, and combine reject duplicate serialized
identities before rendering, leaving existing output unchanged on validation
failure. Version 3.3.0 added opt-in rename-only file update durability. Version
3.6.0 exposed compact CLDR root collation keys without catalog dependencies.

## Upgrade routine

1. Read the `ferrocat` changelog for the target version.
2. If you use direct sub-crates, read their matching changelogs too.
3. Update all Ferrocat crate requirements to the same version line.
4. Run `cargo update -p ferrocat -p ferrocat-po -p ferrocat-icu` when those
   packages are present in your lockfile.
5. Run your normal test suite plus the Ferrocat APIs you call in release or CI
   paths.

When a future release needs a durable migration note — for example a major
version with breaking changes — this page should link that note from the upgrade
routine instead of leaving it buried in a PR.

## Upgrading to 2.1.0

Ferrocat 2.1.0 includes a reviewed cleanup window for accidental public API
coupling left after 2.0.0. These are source-level breaks, but they are small
renames or construction changes with direct replacements.

### Renamed entry points

| Before                  | After                      |
| ----------------------- | -------------------------- |
| `catalog_review`        | `review_catalogs`          |
| `catalog_coverage`      | `measure_catalog_coverage` |
| `has_selectordinal`     | `has_select_ordinal`       |
| `MergeExtractedMessage` | `MergeMessageInput`        |

Search for the old name in compiler errors and replace it with the matching new
name. The `MergeExtractedMessage` compatibility alias was removed, so direct type
annotations need to move to `MergeMessageInput`.

### `MsgStr` accessors

`MsgStr::first()` now returns `Option<&str>`, and iterator items are `&str`. Code
that previously used `first_str()` should call `first()` and handle the empty
translation case explicitly:

```rust
let Some(text) = message.msgstr.first() else {
    return;
};
```

Iteration no longer needs an extra string conversion:

```rust
for variant in message.msgstr.iter() {
    println!("{variant}");
}
```

### `PoVec` construction

`PoVec` is now an opaque inline-vector newtype instead of exposing
`SmallVec<[T; 1]>` in public signatures. Reading is still slice-like, but
constructing affected fields from a `Vec` now needs `From<Vec<T>>` or `.into()`:

```rust
message.origin = vec![CatalogOrigin {
    file: "app.ftl".into(),
    scope: "checkout.title".into(),
}]
.into();
```

Direct equality checks against a `Vec` should compare slices instead:

```rust
assert_eq!(message.origin.as_slice(), expected_origins.as_slice());
```

### Non-exhaustive options

The public options structs are now `#[non_exhaustive]`. Downstream code can no
longer use functional-record-update syntax such as `..Options::new()` outside
the defining crate. Start from `new()` and use the builder methods instead:

```rust
let options = UpdateCatalogOptions::new()
    .with_mode(CatalogMode::IcuPo)
    .with_obsolete_strategy(ObsoleteStrategy::Keep);
```

This keeps future options additive without forcing another public constructor
break.

## API cleanup shipped in 2.1.1

Ferrocat 2.1.1 removed the remaining cross-product entry points for ICU syntax
policy and folded those choices into the existing options structs. The same API
remains supported in later releases. If your code called a `_with_icu_options` or
`_with_syntax_policy` function variant, move the ICU configuration onto the
operation's options value instead.

For catalog audits, build `CatalogAuditOptions` with embedded
`CatalogAuditIcuOptions`:

```rust
use ferrocat::{CatalogAuditIcuOptions, CatalogAuditOptions, IcuSyntaxPolicy};

let options = CatalogAuditOptions::new("en").with_icu_options(
    CatalogAuditIcuOptions::new()
        .with_syntax_policy(IcuSyntaxPolicy::RuntimeLiteralApostrophes),
);
```

For runtime artifact compilation, use `CompileCatalogArtifactOptions`:

```rust
use ferrocat::{
    CompileCatalogArtifactIcuOptions, CompileCatalogArtifactOptions,
    IcuSyntaxPolicy,
};

let options = CompileCatalogArtifactOptions::new("de", "en").with_icu_options(
    CompileCatalogArtifactIcuOptions::new()
        .with_syntax_policy(IcuSyntaxPolicy::RuntimeLiteralApostrophes),
);
```

For pseudolocalization of compiled artifacts, pass the syntax policy through
`CompiledCatalogPseudolocalizationOptions`:

```rust
use ferrocat::{CompiledCatalogPseudolocalizationOptions, IcuSyntaxPolicy};

let options = CompiledCatalogPseudolocalizationOptions::new()
    .with_syntax_policy(IcuSyntaxPolicy::RuntimeLiteralApostrophes);
```

Diagnostic report fields now use the `DiagnosticCode` newtype in Rust instead
of plain `String`. Existing JSON consumers do not need to change: reports still
serialize diagnostic codes as the same canonical strings, for example
`"catalog.missing_translation"`. Rust code that stores or compares codes should
use `code.as_ref()`, `code.to_string()`, the exported `diagnostic_codes`
constants, or direct comparison with a string literal:

```rust
use ferrocat::diagnostic_codes::catalog;

if diagnostic.code == catalog::MISSING_TRANSLATION {
    // Handle missing translations.
}
```
